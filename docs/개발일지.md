## 0단계 · 환경 확인에서 먼저 걸린 것들

코드를 짜기 전에 환경부터 확인했는데, 기획서가 전제한 것과 다른 점이 세 가지 있었습니다.

### git이 PATH에 없었다

`git --version` 이 `command not found` 로 실패했습니다. 그런데 `.git` 폴더는 있고 remote도 설정돼 있었습니다.
찾아보니 Visual Studio가 번들로 설치한 git이 있었습니다.

```
C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\
  CommonExtensions\Microsoft\TeamFoundation\Team Explorer\Git\cmd\git.exe
```

전체 경로로 호출해서 작업했습니다. 깔끔한 해결은 Git for Windows를 따로 설치하는 것입니다.

### Python이 3.9였다

Python 3.9.13이 설치돼 있었습니다. 3.9는 이미 지원이 끝난 버전이라 `google-auth` 가 실행할 때마다 경고를 띄웁니다.

```
FutureWarning: You are using a Python version 3.9 past its end of life.
```

**동작에는 문제가 없어서 그대로 진행했습니다.** 파이썬을 새로 설치하는 것은 이 프로젝트 범위를 넘어서는 시스템 변경이고,
필요한 패키지가 전부 3.9에서 설치·동작하는 것을 확인했기 때문입니다.
다만 코드에서는 3.10 이상에서만 되는 문법(`list[str]` 같은 내장 제네릭)을 피하고 `typing.List` 를 썼습니다.

### 기획서가 지정한 SDK가 지원 종료 상태였다

기획서는 `google-generativeai` 를 쓰라고 했는데, 이 패키지는 Google이 **2025년 8월에 지원 종료를 공지한 레거시 SDK**입니다.
현재 공식 후속은 `google-genai` 입니다.

기획서를 그대로 따를지, 최신 SDK를 쓸지 판단이 필요해서 **물어보고 결정했습니다.** → `google-genai` 채택.

두 SDK는 함수 호출이라는 개념은 같지만 표기가 꽤 다릅니다.

```python
# 레거시 (google-generativeai)
import google.generativeai as genai
genai.configure(api_key=...)
model = genai.GenerativeModel("gemini-2.0-flash", tools=[...])

# 현재 (google-genai)
from google import genai
client = genai.Client(api_key=...)
client.models.generate_content(model=..., contents=..., config=types.GenerateContentConfig(tools=[...]))
```

## 2단계 · 기획서에 안 적혀 있던 것 — 괴리의 "방향"

기획서 3장 ③번 도구 설명은 이렇습니다.

> 두 점수 차이가 임계값(예: 1.5점) 이상이면 "과장 리뷰 가능성 높음"으로 판단

여기서 **"차이"가 절댓값인지 부호 있는 값인지** 가 명시돼 있지 않았습니다. 두 해석이 가능합니다.

| 해석 | 별점 5 / 감성 2 | 별점 1 / 감성 4 |
|---|---|---|
| 절댓값 | 과장 | **과장** (?) |
| 부호 유지 | 과장 | 과장 아님 |

별점 1점인데 내용이 긍정적인 걸 "과장 리뷰"라고 부르는 건 말이 안 됩니다. 그건 오히려 반대 현상입니다.
그래서 **부호를 유지해서 과장은 양수 방향으로만 판정**하고, 반대 방향은 `is_understated` 라는 별도 플래그로 함께 돌려주기로 했습니다.

```python
gap = actual_rating - sentiment_score   # 부호 유지

is_exaggerated = gap >= threshold       # 별점이 후하다 → 과장
is_understated = gap <= -threshold      # 별점이 박하다 → 과소평가
```

두 해석 모두의 정보를 잃지 않으면서, "과장"이라는 단어는 상식에 맞게 씁니다.

### 이 도구에 LLM을 쓰지 않은 이유

기획서에도 명시돼 있지만, 이유를 다시 정리하면:

- 뺄셈 한 번과 비교 두 번이면 끝나는 일입니다.
- LLM은 같은 입력에 다른 답을 줄 수 있지만, 이 계산은 **항상 같은 답이 나와야** 합니다.
- 무료 등급 호출 횟수를 아낍니다.
- **API 키 없이 테스트할 수 있습니다.** 실제로 이 덕분에 키를 받기 전에 31개 테스트를 먼저 통과시킬 수 있었습니다.

### 경계값을 테스트로 고정한 이유

`gap == threshold` 일 때 과장인가 아닌가? 기획서는 "이상"이라고 했으니 포함입니다.
이런 건 나중에 코드를 고치다 실수로 `>` 로 바꾸기 쉬워서, 테스트로 못 박아 뒀습니다.

```python
def test_기준치와_정확히_같은_괴리도_과장으로_판단한다(self):
    result = detect_review_exaggeration(actual_rating=5, sentiment_score=3.5, threshold=1.5)
    assert result["gap"] == 1.5
    assert result["is_exaggerated"] is True
```

### NaN을 따로 막은 이유

점수 범위를 `1.0 <= score <= 5.0` 으로 검사했는데, **NaN은 이 검사를 통과해버립니다.**
NaN은 어떤 비교 연산에도 `False` 를 돌려주기 때문에 `not (1.0 <= nan <= 5.0)` 이 `True` 가 되어... 사실 이 경우는 걸립니다.
하지만 비교 방향이 조금만 달라지면 그냥 통과합니다. 헷갈리는 함정이라 명시적으로 막고 테스트도 붙였습니다.

```python
if score != score:  # NaN은 자기 자신과도 같지 않다
    raise ValueError(...)
```

## 3단계 · 재시도를 어디에 넣을 것인가

무료 등급에서는 429(한도 초과)가 흔합니다. 재시도 로직을 **도구마다 따로 넣을지, 한 곳에 모을지** 결정해야 했습니다.

도구마다 넣으면 나중에 한 곳을 고칠 때 다른 곳을 빠뜨립니다. 그래서 **모든 API 호출이 `gemini_client.generate()` 를 거치도록** 하고, 재시도는 거기 한 군데만 뒀습니다.

### 재시도해야 할 오류와 하면 안 되는 오류

전부 재시도하면 안 됩니다. API 키가 틀렸는데 4번 더 시도해봐야 4번 다 틀립니다.

| 코드 | 의미 | 재시도 |
|---|---|---|
| 429 | 한도 초과 | O — 기다리면 열린다 |
| 500, 503, 504 | 서버 일시 오류 | O — 잠깐 뒤엔 될 수 있다 |
| 400 | 요청 형식 오류 | X — 다시 보내도 똑같이 틀리다 |
| 401, 403 | 키/권한 문제 | X — 키를 고쳐야 한다 |
| 404 | 모델 없음 | X — 모델 이름을 고쳐야 한다 |

### 지터(jitter)를 넣은 이유

백오프를 정확히 2초, 4초, 8초로 하면 **여러 요청이 동시에 실패했을 때 똑같은 시점에 몰려서 다시 시도**합니다.
그러면 또 같이 한도에 걸립니다. 그래서 대기 시간에 최대 25%의 무작위성을 더했습니다.

```python
delay = min(BASE_DELAY_SEC * (2 ** attempt), MAX_DELAY_SEC)
return delay + random.uniform(0, delay * 0.25)
```

### 테스트에서 실제로 기다리지 않게 하기

재시도 테스트를 그냥 돌리면 2+4+8 = 14초씩 걸립니다. `time.sleep` 을 가로채서 **호출된 대기 시간을 기록만 하게** 했습니다.
덕분에 테스트는 즉시 끝나면서, 백오프가 실제로 늘어나는지도 검증할 수 있습니다.

```python
@pytest.fixture(autouse=True)
def no_sleep(monkeypatch):
    recorded = []
    monkeypatch.setattr(gemini_client.time, "sleep", recorded.append)
    return recorded
```

## 4단계 · LLM에게 JSON을 안정적으로 받아내기

도구 ①②는 결과를 JSON으로 받아야 합니다. 프롬프트로 "JSON으로 답해줘"라고만 하면 이런 게 섞여 옵니다.

- ` ```json ... ``` ` 처럼 마크다운으로 감싼 응답
- `{"pros": "배송이 빠름"}` — 리스트여야 할 자리에 문자열 하나
- `{"score": "매우 좋음"}` — 숫자여야 할 자리에 문자열
- `{"score": 7}` — 범위를 벗어난 값

`response_schema` 로 구조를 강제하면 대부분 해결되지만, **모델이 스키마를 100% 지킨다고 가정하면 안 됩니다.** 그래서 안전망을 겹으로 뒀습니다.

1. `response_mime_type="application/json"` + `response_schema` 로 구조 강제
2. 코드 블록 표기가 붙어 오면 벗겨냄
3. 리스트 자리에 문자열이 오면 리스트로 감쌈
4. 빈 문자열·null·중복 제거
5. 점수가 범위를 벗어나면 1~5로 자름(clamp)

### 4번 clamp가 특히 중요했던 이유

도구 ②의 출력이 도구 ③의 입력으로 들어갑니다. 도구 ③은 1~5 범위를 벗어나면 `ValueError` 를 냅니다.
즉 **모델이 7점을 주면 다음 도구에서 터집니다.** 경계에서 막아두지 않으면 사용자는 "왜 갑자기 에러가 나지?" 하게 됩니다.

이 연결을 테스트로도 고정해 뒀습니다.

```python
def test_결과가_도구3에_바로_넘어갈_수_있다(self, fake_gemini):
    sentiment = tools.score_sentiment("배송도 늦고 품질도 별로예요.")
    report = tools.detect_review_exaggeration(5, sentiment["score"])
    assert report["is_exaggerated"] is True
```

### 길이 검사를 API 호출 전에 한 이유

리뷰가 2000자를 넘으면 어차피 실패합니다. **호출한 뒤에 실패하면 무료 등급 한도만 낭비**합니다.
그래서 길이 검사는 API를 부르기 전에 하고, 테스트로도 "거부됐을 때 API가 호출되지 않았음"을 확인합니다.

```python
assert fake_gemini.calls == []  # API를 낭비하지 않는다
```

### temperature를 0.1로 낮춘 이유

리뷰에서 장단점을 뽑아내는 일에는 창의성이 필요 없습니다. 오히려 **같은 리뷰에 같은 답이 나오는 게 중요**합니다.
온도를 낮추면 결과가 안정되고, 테스트하기도 쉬워집니다.

## 5단계 · 자동 함수 호출을 일부러 껐다

`google-genai` SDK에는 파이썬 함수를 그대로 `tools=[my_func]` 로 넘기면 **SDK가 알아서 호출까지 해주는** 기능이 있습니다.
코드는 훨씬 짧아집니다. 그런데 이걸 끄고 루프를 직접 짰습니다.

```python
automatic_function_calling=types.AutomaticFunctionCallingConfig(disable=True)
```

이유는 **"에이전트가 도구를 골라 호출했다"는 걸 눈으로 보여주기 위해서**입니다.
SDK에 맡기면 호출 기록이 안쪽에서 처리돼 화면에 표시할 수 없습니다.
직접 루프를 돌리면 어떤 도구를 어떤 인자로 불렀는지 전부 기록해서 화면 하단에 펼쳐 보여줄 수 있습니다.

이 프로젝트의 핵심이 "에이전트가 도구를 쓴다"는 것이므로, 코드 몇 줄 더 쓰는 값어치가 있다고 판단했습니다.

### threshold를 모델이 정하지 못하게 막았다

도구 ③의 스키마에서 `threshold` 를 일부러 **뺐습니다.** 모델이 "이번엔 2점을 기준으로 하죠" 하고 마음대로 정하면 안 되기 때문입니다.
임계값은 사용자가 사이드바에서 정하는 앱 설정값이므로, 호출 직전에 코드가 강제로 주입합니다.

```python
if name == "detect_review_exaggeration":
    args["threshold"] = threshold   # 모델이 뭘 넣었든 덮어쓴다
```

테스트로도 고정했습니다 — 모델이 `threshold: 0.1` 을 넣어도 앱 설정값 `2.0` 이 이깁니다.

### 도구가 실패해도 예외를 던지지 않는다

도구 실행이 실패하면 예외를 밖으로 던지는 대신, **오류 내용을 모델에게 돌려줍니다.**

```python
record["response"] = {"error": record["error"]}
```

그러면 모델이 "분류에 실패했습니다"라고 상황을 설명하거나 다시 시도할 수 있습니다.
사용자 입장에서는 앱이 통째로 죽는 것보다 훨씬 낫습니다.

### 무한 루프 차단

모델이 같은 도구를 계속 부르며 끝나지 않을 수 있습니다. `MAX_TURNS = 6` 으로 상한을 두고, 초과하면 안내 메시지와 함께 중단합니다.
이것도 테스트로 확인합니다 — 모델이 6번 연속 도구를 부르는 대본을 만들어 `AgentError` 가 나는지 봅니다.

## 6단계 · 화면에서 신경 쓴 것

### 눌러봐야 실패할 버튼은 아예 안 띄운다

API 키가 없으면 분석은 100% 실패합니다. 그런데 입력 폼과 버튼을 보여주면 사용자는 리뷰를 다 입력하고 버튼을 누른 뒤에야 실패를 알게 됩니다.
그래서 키가 없을 때는 **입력 폼 대신 설정 안내 화면만** 띄웁니다.

```python
if not has_api_key():
    _render_api_key_guide()
    return
```

### 오류의 성격에 따라 색을 다르게

- **노란 경고(warning)** — 사용자가 고칠 수 있는 것 (리뷰가 너무 짧다/길다)
- **빨간 오류(error)** — 사용자가 당장 못 고치는 것 (한도 초과, API 오류)

"리뷰가 5자 이상이어야 합니다"를 빨간 오류로 띄우면 뭔가 크게 잘못된 것처럼 보입니다. 그냥 몇 자 더 쓰면 되는 일입니다.

### 도구 호출 기록에서 리뷰 원문을 잘라서 보여준다

도구 인자에 리뷰 원문이 통째로 들어가서, 그대로 표시하면 화면이 리뷰로 도배됩니다. 60자에서 자르고 `...` 을 붙였습니다.

## 6단계 · 테스트에서 막혔던 것 — AppTest와 monkeypatch

Streamlit 화면을 테스트하려고 공식 도구인 `AppTest` 를 썼는데, **6개 테스트가 전부 빈 결과를 반환**했습니다.

```python
import app as app_module
monkeypatch.setattr(app_module, "analyze_review", 가짜함수)   # 안 먹힘
```

원인은 **`AppTest` 가 `app.py` 를 별도 네임스페이스로 매번 다시 실행**한다는 것이었습니다.
`sys.modules['app']` 에 있는 모듈을 패치해봐야, `AppTest` 가 새로 실행하는 스크립트와는 다른 객체입니다.

해결은 **원본 쪽을 패치**하는 것이었습니다. `app.py` 는 `from src.agent import analyze_review` 로 가져가므로,
`src.agent.analyze_review` 를 바꿔두면 다시 실행될 때 바뀐 함수가 잡힙니다.

```python
monkeypatch.setattr("src.agent.analyze_review", 가짜함수)   # 이건 먹힘
```

같은 실수를 반복하지 않도록 테스트 파일에 주석으로 이유를 남겼습니다.

### 검증하지 못하는 테스트를 하나 발견해서 고쳤다

에이전트 테스트를 쓰다가 이런 걸 만들어놨었습니다.

```python
def test_자동_함수호출은_꺼져있다(self, ...):
    config = scripted_gemini.contents_history and None
    assert config is None   # 이건 항상 통과한다
```

`config` 가 항상 `None` 이라 **무조건 통과하는 가짜 테스트**였습니다.
가짜 Gemini가 `config` 인자도 기록하도록 고치고, 실제로 `automatic_function_calling.disable` 이 `True` 인지 확인하도록 바꿨습니다.

## 테스트를 134개나 쓴 이유

이 프로젝트에서 실제 API를 부르는 테스트는 **0개**입니다. 전부 가짜 Gemini로 돌립니다.

처음엔 "API를 안 부르면 진짜 테스트가 아니지 않나" 싶었는데, 반대였습니다.

- **무료 등급 한도를 안 씁니다.** 테스트를 100번 돌려도 API 사용량이 0입니다.
- **API 키 없이 돌아갑니다.** 다른 사람이 저장소를 받아도 바로 테스트할 수 있습니다.
- **빠릅니다.** 134개가 2초 안에 끝납니다.
- **재현됩니다.** 실제 API는 같은 입력에 다른 답을 주지만, 가짜는 항상 같습니다.

실제 API 연동은 테스트가 아니라 `scripts/check_connection.py` 와 실제 사용으로 확인합니다. 역할을 나눈 것입니다.

## 커밋을 단계별로 나눈 이유

기획서 7단계에 "단계별로 나눠서 커밋"이 명시돼 있기도 하지만, 실제로 도움이 됐습니다.
6단계에서 `AppTest` 문제로 막혔을 때, 앞 단계가 전부 커밋돼 있어서 **어디까지가 확실히 동작하는 상태인지** 분명했습니다.

커밋 메시지에는 "무엇을 했는지"보다 **"왜 그렇게 했는지"** 를 적었습니다.
`feat: 도구3 구현` 만 있으면 나중에 봤을 때 왜 과장 판정을 양수 방향으로만 했는지 알 수 없습니다.

### 중간에 겪은 사소한 사고

커밋 메시지에 큰따옴표가 들어가니까 PowerShell here-string이 깨져서, git이 메시지 일부를 파일 경로로 착각했습니다.

```
error: pathspec '도구를' did not match any file(s) known to git
```

메시지를 파일로 저장하고 `git commit -F 파일` 로 넘기는 방식으로 바꿔 해결했습니다.
